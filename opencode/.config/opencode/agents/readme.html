What team-lead actually does

Think CEO, not IC. Incoming work is either a raw user request or a Research Brief from researcher. Vague work gets refined first. Clear work gets classified, then dispatched with subagent(agent=...). Each dispatch is a fresh call: wait, evaluate the handover status, then continue. Mixed app-plus-infra work splits and runs in parallel.

Does

Classify, dispatch, synthesize

Pick domain (dev / ops / both), dispatch the pipeline lead, merge handovers into a user-facing report: what changed, decisions, files, next steps, BLOCK items.

Does not

Write the change itself

No application code, no GitOps manifests, no cluster mutation. Never skip to an engineer. If a pipeline lead returns [REWORK], resume that child session with sessionID= and error context. If [BLOCK], stop and show the user.

What happens when you talk to team-lead

You never pick a specialist. You talk to team-lead. It decides who to call, waits for each handover, then answers you. Nested agents only talk to their parent — they do not chat with you.

  1. You describe the work. If it is already a Research Brief, skip intake.
  2. If the ask is vague, team-lead dispatches researcher first.
  3. It classifies domain: software, infra, or both.
  4. It always dispatches dev-team-lead and/or devops-team-lead. Mixed work runs both in parallel. It cannot call engineers directly.
  5. Approval Gate — before the first dispatch, it presents the approach, the files to touch, and the trade-offs it rejected, then waits for your go-ahead. Once-per-task: one approval covers the whole pipeline.
  6. Each child may dispatch further (shown in the tree). Results bubble back up as a handover.
  7. team-lead checks status: [SUCCESS] → report to you; [REWORK] → retry via sessionID= (max 2); [BLOCK] → stop and ask you.
Domain

Software vs infra vs mixed

Software: app code, features, bugs, UI, APIs, schema, tests.
Infra: Flux/GitOps, Kubernetes, Helm, storage, ingress, CI/CD.
Mixed: split, fire both branches, merge the report.

Always

Through the pipeline lead

Same stages: design → implement → verify → docs → post-verification. Intake sits above both. Leads [BLOCK] if the ask is still vague.

Click any node. Results return to the parent, then to team-lead, then to you.

Dispatch goes through subagent(agent=...) and is capped at two layers from team-lead by experimental.subagent_depth: 2 in opencode.json. Software: team-lead → dev-team-lead → backend-engineer is the deepest chain. Infra: team-lead → devops-team-lead → devops-engineer is the deepest. The post-verification agents (devops-cleanup, post-mortem-analyst) are dispatched directly by team-lead at that same depth. Rework does not restart the call chain: the pipeline lead resumes the failed child session with sessionID= plus the error context.

Approval Gate

Step 1.5 sits between classification and dispatch. team-lead presents the approach, the files it will touch, and the trade-offs it rejected — then waits for an affirmative reply before the first subagent() call of a pipeline lead, or before any state-mutating change. Read-only work (diagnosis, research, researcher dispatch, listing options) stays free without approval.

The gate is once per task: one approval covers the whole pipeline lead and everything downstream of it. It is not re-asked at each stage. Re-approval is only required if scope drifts — more files than approved, a different approach, a new dependency or tool not named in the approval, or a wider blast radius.

  1. You describe the work. If it is already a Research Brief, skip intake.
  2. If the ask is vague, team-lead dispatches researcher first.
  3. It classifies domain: software, infra, or both.
  4. Approval Gate — present approach, files, trade-offs; wait for your go-ahead.
  5. It dispatches dev-team-lead and/or devops-team-lead. Mixed work runs both in parallel.
  6. Each child may dispatch further (shown in the tree). Results bubble back up as a handover.
  7. team-lead checks status: [SUCCESS] → report to you; [REWORK] → retry via sessionID= (max 2); [BLOCK] → stop and ask you.

How agents talk

Every specialist returns the handover protocol (signal, not the raw log dump). team-lead then translates that into a human summary and keeps a TRACE of the chain.

[SUCCESS] Done as asked. Synthesize and report.
[REWORK] Re-dispatch with error context. Max 2. Then escalate.
[BLOCK] Human needed. Halt. Do not route around it.

What gets passed down

Refined task, constraints, expected output. Not full chat history, not raw exploration dumps, not internal routing notes.

Outside the team-lead chain

Live at top level as agents/*.md, in the same folder as the pipeline agents — the old common/, dev/, and devops/ subfolders no longer exist. docs is also top level (agents/docs.md) and is the one shared stage dispatched by both pipeline leads after verification returns [SUCCESS]. team-lead does not dispatch the auditors below — invite one yourself for an audit or cleanup.

  • ai-security-auditor

    Looks through the codebase for vulnerabilities.

  • context-drift-auditor

    Verifies / audits context drift and code structure.

  • architecture-cleanup

    Audits architectural drift and dependency violations, then systematically tidies up.

  • performance-auditor

    Audits codebase performance.

  • seo-aeo-auditor

    SEO / AEO audit and verification.

  • test-auditor

    Test-quality validation (separate from test-engineer).
